Chapter 1: INTRODUCTION 
1.1 Background 
Modern distributed computing environments have grown dramatically more complex. 
Today's systems often include hundreds of microservices and thousands of 
interconnected nodes deployed across multiple locations, each generating continuous 
streams of telemetry data that record internal and external behavior in real time. System 
logs represent one of the most important data streams. They provide the primary record 
of system operations, the first indication of performance degradation, and, when properly 
analyzed, a forensic trail to root causes before failures escalate into outages. He et al. 
(2020) found that fault-tolerant distributed systems can generate terabytes of logs daily. 
Operations teams face not a shortage of diagnostic information, but rather the challenge 
of processing and interpreting it as quickly as it arrives and at sufficient scale. 
Automated log analysis has evolved from hand-crafted rules to statistical machine 
learning and, more recently, to deep learning and large language models. Early systems 
relied on manually specified regular expressions (Du et al., 2017). Machine learning 
brought data-driven detection. Xu et al. (2009) applied Principal Component Analysis to 
Hadoop Distributed File System logs. Liu et al. (2008) introduced Isolation Forest for 
unsupervised anomaly detection. These techniques improved coverage by learning from 
historical data rather than being limited to pre-defined patterns. Deep learning models 
like DeepLog (Du et al., 2017) and LogBERT (Guo et al., 2021) achieved F1-scores near 
0.98 on standard datasets. Despite these advances, two problems persist: limited 
interpretability and inability to use external contextual knowledge at inference time. 
1.2 Problem Statement 
Existing automated log analysis systems struggle to achieve accurate, timely, and 
interpretable anomaly detection at the scale modern distributed infrastructure demands. 
To understand this problem, we must examine both its practical consequences and the 
specific technical limitations that sustain it. 
The cost of failing to identify system anomalies in production environments is 
substantial. Gartner (2023) reports that unplanned IT infrastructure downtime costs 

approximately $5,600 per minute. Mean Time to Detect (MTTD)—the interval between 
fault occurrence and detection by monitoring systems—is a fundamental reliability metric 
(Patterson, 2002). In organizations using rule-based log analysis, MTTD can extend to 
tens of minutes or hours when failure modes fall outside pre-specified pattern libraries. 
Improved automated detection can reduce MTTD to seconds. In financial trading 
systems, healthcare platforms, or e-commerce environments, the difference between 
detection in seconds versus minutes can mean substantial data loss, regulatory exposure, 
and reputational damage. 
Existing automated approaches fail to bridge this gap for three well-documented reasons: 
1. Inflexibility and high false positive rates: Rule-based log analysis, the most widely 
deployed method in practice, matches log content against predefined pattern libraries. If a 
failure type was not anticipated when rules were created, it goes undetected, leading to 
false negatives and allowing failures to escalate. The high false positive rate, exceeding 
thirty percent in practice (Du et al., 2017), compounds this problem. Practitioners 
experience "alert fatigue"—a well-documented condition where genuine alerts are 
deprioritized or ignored (Sommer and Paxson, 2010). The maintenance burden 
aggravates these difficulties, as rule libraries must be manually updated as system 
architecture evolves. 
2. Lack of interpretability: While machine learning and deep learning have improved 
accuracy in log data analysis, they introduce a new challenge: lack of interpretability. 
Approaches like Isolation Forest, PCA, and LSTM-based networks can classify log 
sequences as anomalous or normal and provide numerical scores, but offer no 
justification. For an operator receiving a warning based on a detected anomaly, an 
anomaly score provides little actionable information. There is no way to determine 
whether the anomaly relates to a network timeout, memory leak, or authentication 
problem. This directly impacts MTTD. Chen et al. (2023) argue that anomaly detection 
systems must be evaluated not only on accuracy but also on interpretability. 
3. Knowledge isolation and hallucination: All approaches mentioned share the 
limitation of being closed systems—their analytical capabilities are limited to information 

encoded in the system or programmed by rule authors. When interpreting a suspicious log 
pattern requires knowledge of a recently discovered vulnerability, a known interaction 
between system components, or a historical event in a similar system, these approaches 
cannot access that information. Large language models (LLMs) partially address this 
through broad knowledge encoded in model parameters, but they suffer from a well-
known failure mode: hallucination. Ji et al. (2023) demonstrated that LLMs generate 
factually incorrect output with high confidence in technical domains. 
The cumulative effect of these three limitations creates a monitoring environment where 
organizations face a three-part tradeoff: fast but often wrong, accurate but unclear, or 
seemingly competent but unreliable. No solution currently addresses all three issues 
adequately. Table 1.1 compares existing approaches with the proposed system on

What is required and has not been implemented or tested before—is a system that 
combines the contextual knowledge base of retrieval-augmented systems with the 
iterative and adaptive reasoning properties of agentic artificial intelligence. Such a system 
would draw upon external knowledge sources, adjust its analytical approach based on 
interim results, and produce outputs that are both correct and useful to those responsible 
for acting on them. This dissertation proposes and tests such a system. 

1.3 Proposed Solution 
This dissertation introduces an Agentic Retrieval-Augmented Generation (RAG) 
framework for system log analysis designed to overcome the three limitations identified 
in Section 1.2. The framework comprises four components. First, a log preprocessing 
module normalizes system log entries into structured formats using the Drain3 algorithm 
(He et al., 2017), parsing entries with severity levels, system components, and log 
templates while masking variable contents. Second, a vector-based knowledge base using 
the FAISS library stores domain knowledge documents, error patterns, and historical 
incident reports. Third, an agentic controller implements the ReAct pattern (Yao et al., 
2023), capable of up to five iterative reasoning steps per log entry and autonomously 
deciding which process is needed at each step: retrieving knowledge, revising severity 
assessment, or producing a structured alert. Fourth, an alert generator produces human-
readable structured alerts with complete reasoning chains, involved components, 
confidence levels, and recommended actions. 
The proposed system differs from conventional RAG and other log analysis 
methodologies through its iterative reasoning capability. While standard RAG retrieves 
information and generates a response in a single step, the proposed system adapts its 
responses based on findings during the reasoning process. This mirrors the approach of 
an experienced system engineer who would iteratively reason about possible 
consequences and determine the most appropriate action. The system seeks to reduce 
MTTD through automated contextual analysis in seconds while addressing alert quality 
by providing context to operators, enabling them to take necessary action without further 
investigation. 
1.4 Research Questions 
The limitations identified in Section 1.2 and the solution proposed in Section 1.3 led to 
three research questions that frame the empirical investigation in this dissertation: 
RQ1: Does the agentic RAG approach improve accuracy for anomaly detection in system 
log analysis compared to non-agentic RAG and rule-based approaches based on 
precision, recall, F1-score, and false positive rate on HDFS and BGL benchmark data? 

RQ2: Which baseline system approach—rule-based, Isolation Forest, or non-agentic 
RAG—shows the greatest competitiveness compared to the proposed agentic RAG 
framework, and what aspects account for performance variations in detecting anomalies? 
RQ3: Does the proposed agentic RAG system demonstrate greater alert specificity 
compared to the rule-based approach based on qualitative evaluation using a rubric 
measuring component identification, root cause explanation, and recommendation 
specificity? 
Research Question 1 addresses effectiveness—whether multi-step agentic reasoning 
based on retrieved knowledge outperforms existing approaches for detection. Research 
Question 2 identifies which baseline approach best approximates the proposed system 
and why, helping determine whether the computational cost of agentic reasoning proves 
worthwhile or whether a simpler machine learning approach achieves similar results. 
Research Question 3 shifts focus to qualitative aspects of alert quality for operators 
affected by system-generated alerts, a factor not captured in quantitative precision and 
recall measures. 
1.5 Aims and Objectives 
The main aim of this dissertation is to design, implement, and evaluate an agentic RAG 
framework for system log analysis that overcomes the interpretability, flexibility, and 
knowledge grounding limitations of existing techniques, and to provide empirical 
evidence for the effectiveness of the proposed approach in comparison with three 
baselines. 
Seven specific objectives follow from this aim: 
O1: To conduct a critical review of the literature on system log analysis techniques, 
including rule-based systems, machine learning, deep learning, RAG, and agentic AI 
systems, and to identify the specific limitations of existing techniques that the proposed 
approach addresses. 

O2: To develop an agentic RAG system architecture that addresses the three identified 
issues through a knowledge retrieval mechanism, a multi-step ReAct reasoning 
controller, and a structured alerts generator. 
O3: To implement the proposed framework as a working research prototype using 
Python, LangChain, FAISS, Drain3, and Mistral 7B through Ollama. 
O4: To implement three comparative baseline system prototypes: a rule-based keyword 
matcher system, an Isolation Forest classifier system, and a non-agentic single-pass RAG 
system. 
O5: To evaluate all developed system prototypes on the HDFS and BGL datasets with 
standardized detection performance metrics (Precision, Recall, F1-score, False Positive 
Rate) and perform paired t-tests to determine statistical significance, addressing RQ1. 
O6: To analyze the comparative detection performance results and determine which 
baseline system performs closest to the proposed framework, addressing RQ2. 
O7: To analyze the quality of alerts generated by the agentic RAG system and the rule-
based system by comparing a sample set using a standardized rubric to determine 
component identification, root cause explanation, and recommendation specificity, 
addressing RQ3.

Chapter 2: LITERATURE REVIEW 
2.1 Introduction 
The literature on automated log analysis spans several decades and has evolved 
considerably in recent years, driven by advances in natural language processing and the 
availability of open benchmark datasets. Development has been particularly rapid since 
2020, with transformer-based models, large language models, and retrieval-augmented 
generation entering the log analysis research agenda. This chapter reviews the relevant 
body of work across five areas: traditional log analysis methods, deep learning 
techniques, large language models, retrieval-augmented generation, and agentic AI. The 
chapter examines evaluation frameworks used to benchmark these approaches and 
concludes by identifying the specific gap this research addresses. 
2.2 Rule-Based Log Analysis 
Rule-based log analysis remains the most widely deployed category of automated 
monitoring in production environments, reflecting both its operational simplicity and the 
inertia of established tooling rather than technical superiority over recent approaches. The 
fundamental mechanism is straightforward: system administrators define patterns—
typically regular expressions or keyword lists—that correspond to known failure 
signatures. When a log entry matches a pattern, an alert is raised. The approach requires 
no training data, executes in microseconds, and produces results that are, in principle, 
fully transparent and auditable. 
He et al. (2020), in a comprehensive survey of automated log analysis techniques, 
characterize rule-based systems as occupying a necessary but fundamentally constrained 
role. Their central limitation is the closed-world assumption: the system can only detect 
what it has been explicitly instructed to look for. In fast-moving deployment 
environments where software components, infrastructure configurations, and operational 
patterns evolve continuously, novel failure modes—precisely those most likely to be 
consequential—pass entirely undetected. Maintaining comprehensive and current rule 
libraries becomes a substantial operational burden, and available evidence suggests most 
organizations fall short of complete coverage. 

Le and Zhang (2022) provide direct empirical evidence of this limitation through 
systematic evaluation of log parsing and analysis methods across multiple datasets 
exhibiting label noise, format drift, and template evolution—conditions representative of 
live production systems. Their findings demonstrate that rule-based approaches 
experience consistent performance degradation as log formats evolve, and that the gap 
between benchmark results on clean datasets and real-world performance is considerably 
wider for rule-based systems than for data-driven alternatives. 
The false positive problem compounds these concerns. Keyword-based pattern matching 
cannot reliably distinguish between a log entry containing ERROR as part of a genuine 
unhandled fault and one containing it as part of a successfully handled exception. When 
false positive rates are high—empirical studies suggest rates exceeding thirty percent in 
production environments (He et al., 2020)—the practical consequence is alert fatigue: 
progressive deterioration of operator responsiveness to genuine alerts. Alert fatigue is not 
merely an inconvenience; it is a safety-critical failure mode that can cause genuine high-
severity incidents to be missed or deprioritized precisely because they arrive in a stream 
of predominantly spurious notifications. 
2.3 Machine Learning Approaches 
The limitations of rule-based systems motivated development of data-driven log analysis 
methods capable of learning to distinguish normal from anomalous behavior without 
requiring explicit pattern specification. The machine learning generation introduced 
clustering, dimensionality reduction, and ensemble anomaly detection, all addressing the 
rigidity problem of rule-based approaches by adapting their behavior to statistical 
properties of the log data they were trained on. However, this generation introduced its 
own distinct set of limitations. 
He et al. (2020) survey this generation extensively, noting that methods based on 
statistical features—such as log event frequency counts, inter-arrival time distributions, 
and template co-occurrence patterns—can identify statistical outliers that escape 
keyword-based detection. The principal advantage is adaptability: by learning a 
representation of normal system behavior from historical log data, these methods can 
detect deviations even when the specific failure signature has not been observed before. 

This makes them structurally better suited to novel anomaly detection than rule-based 
systems, at least in principle. 
In practice, however, machine learning approaches introduce two limitations that have 
constrained their adoption. The first is the feature engineering bottleneck. These methods 
require conversion of raw, unstructured log text into numerical feature vectors, and 
detection quality is directly dependent on feature quality. He et al. (2020) note that 
naively constructed features—such as simple term frequency representations—fail to 
capture semantic relationships and sequential dependencies that characterize log data, 
resulting in detection models sensitive to superficial statistical patterns rather than 
underlying operational semantics. The second limitation is more fundamental: machine 
learning methods produce anomaly scores or binary classification outputs with no 
accompanying explanation. An anomaly score of 0.87 provides an operator with no 
information about which component generated the anomalous behavior, what the likely 
cause might be, or what remediation steps would be appropriate. Le and Zhang (2022) 
identify this interpretability gap as one of the most persistent unresolved challenges in the 
log analysis field. 
A further concern specific to unsupervised approaches—which represent the majority of 
deployed machine learning log analysis systems—is calibration sensitivity. If training 
data contains anomalies mislabeled as normal, which is common in environments where 
historical incidents were not systematically documented, the learned model of normal 
behavior will be corrupted. Chen et al. (2023) discuss this as a calibration problem that 
complicates the reliability of machine learning anomaly scores in operational contexts. 
2.4 Deep Learning Methods for Log Analysis 
Deep learning approaches emerged as a response to the feature engineering bottleneck of 
classical machine learning methods. Rather than relying on hand-crafted numerical 
representations, deep learning models learn representations directly from raw log 
sequences, capturing both semantic content of individual log events and sequential 
dependencies between them. This generation achieved substantially higher detection 
accuracy on standard benchmarks and reduced manual effort required for feature design, 

but introduced its own limitations around robustness to real-world conditions and the 
persistent absence of interpretable outputs. 
Guo et al. (2021) introduced LogBERT, applying the BERT transformer architecture to 
log anomaly detection through a two-stage approach: unsupervised pre-training on 
unlabeled log sequences, followed by anomaly detection using the trained 
representations. LogBERT demonstrated F1-scores of 0.982 on the HDFS dataset and 
0.908 on the BGL dataset, representing meaningful improvement over earlier methods 
and establishing transformer-based representations as the state of the art for log anomaly 
detection on standard benchmarks. The innovation was using self-supervised pre-training 
to develop semantic representations of log templates that capture contextual relationships 
between log events—relationships that feature-based methods cannot represent. 
Zhang et al. (2024) contribute complementary work with LILAC, a log parsing approach 
that uses large language models with an adaptive parsing cache to improve the quality of 
structured log representations that downstream analysis methods depend on. Their work 
demonstrates that transformer-based models can contribute to the log preprocessing stage 
as well as the analysis stage, and that log template extraction quality—a step often treated 
as solved in the log analysis literature—has substantial downstream impact on anomaly 
detection performance. This finding is directly relevant to the present research, which 
uses the Drain3 parsing algorithm for preprocessing. 
Despite these accuracy improvements, Le and Zhang (2022) provide a sobering 
assessment of deep learning methods under realistic operating conditions. In systematic 
evaluation across multiple datasets with varying degrees of label noise, format drift, and 
template evolution, they find that performance degrades significantly relative to clean-
benchmark results. Methods achieving near-perfect F1-scores on standard HDFS 
evaluations demonstrate substantially reduced performance when evaluated on logs 
exhibiting the kinds of variation common in live environments. This finding is important 
for interpreting published benchmark results: high accuracy figures reported in many 
papers may reflect performance on idealized evaluation conditions rather than genuine 
operational capability. 

Most critically, the interpretability limitation remains entirely unresolved across all deep 
learning approaches. Transformer models can be probed using attention visualization and 
gradient-based attribution methods, but these techniques do not produce the kind of 
natural language explanation that operations engineers require to make rapid, confident 
triage decisions. Chen et al. (2023) argue that the gap between detection accuracy and 
decision support quality represents one of the most significant barriers to practical 
deployment of deep learning methods in operational monitoring, and that future log 
analysis research must treat interpretability as a primary design requirement rather than 
an optional supplement to detection performance. 
2.5 Large Language Models in Log Analysis 
The emergence of large language models as general-purpose reasoning systems opened a 
new line of inquiry for log analysis researchers. Unlike their predecessors, LLMs can 
generate natural language explanations of their outputs, reason over unfamiliar input 
patterns, and use broad technical knowledge acquired during pre-training on large 
corpora of technical documentation, academic papers, and software engineering content. 
These properties directly address the interpretability limitations of machine learning and 
deep learning methods, making LLMs attractive candidates for log analysis applications 
where human-readable output is required. However, LLMs introduce a qualitatively 
different class of failure mode that demands careful consideration before deployment in 
reliability-critical contexts. 
Ji et al. (2023), in a comprehensive survey of hallucination in natural language generation 
systems, document that LLMs produce factually incorrect outputs with high confidence 
across a wide range of domains, with particularly pronounced failure rates in technical 
and scientific contexts. For log analysis applications, the implications are substantial. A 
system that confidently misdiagnoses a production fault—attributing a network partition 
to database connection pool exhaustion, for example—may actively impede incident 
resolution by directing engineering attention toward the wrong component and delaying 
correct diagnosis. Ji et al. (2023) argue that hallucination in LLMs is not a surface-level 
deficiency that can be eliminated through prompt engineering, but a structural 

consequence of how parametric knowledge is encoded in model weights—knowledge 
that is inherently imprecise, potentially outdated, and unverifiable at inference time. 
Zhang et al. (2024) demonstrate that LLMs can be adapted effectively for the upstream 
log parsing task when combined with an adaptive caching mechanism that stores and 
reuses previously parsed templates. Their LILAC framework achieves parsing accuracy 
competitive with dedicated log parsing tools while providing greater flexibility in 
handling previously unseen log formats. This finding is relevant because it illustrates that 
LLMs can contribute at multiple stages of the log analysis pipeline, not only at the 
analysis and alert generation stage. 
Qi et al. (2023), in an empirical study of LLM-based log anomaly detection using 
ChatGPT-style models, find that prompt engineering and in-context learning techniques 
can improve accuracy of LLM outputs on log classification tasks, but that performance 
remains sensitive to prompt design and deteriorates on log formats that differ 
substantially from those encountered during pre-training. These findings collectively 
suggest that LLMs are a promising but structurally insufficient basis for standalone log 
analysis systems: their interpretability and reasoning capabilities are genuinely valuable, 
but their hallucination risk and sensitivity to input distribution shift are genuine and non-
trivial limitations. 
2.6 Retrieval-Augmented Generation 
Retrieval-Augmented Generation (RAG) was introduced by Lewis et al. (2020) as a 
framework for combining the generative capabilities of large language models with the 
precision of information retrieval from external knowledge sources. The foundational 
insight is that LLM generation need not rely solely on parametric knowledge encoded in 
model weights—knowledge that may be outdated, imprecise, or absent for highly 
specialized domains. By retrieving relevant documents from an external knowledge base 
at inference time and conditioning generation on those documents, RAG grounds the 
model's outputs in verifiable evidence, substantially reducing hallucination rates on 
knowledge-intensive tasks. 

Lewis et al. (2020) demonstrate across multiple question-answering benchmarks that 
RAG consistently outperforms both standalone retrieval systems and standalone LLMs, 
and that the combination produces outputs more factually accurate than either component 
in isolation. The retrieval component—implemented using dense passage retrieval with 
FAISS vector indexing—enables the system to locate relevant documents even when the 
query and target document do not share exact keyword overlap, a capability particularly 
valuable for log analysis where natural language description of a failure pattern may 
differ substantially from technical terminology used in the log entry itself. The generation 
component, conditioned on retrieved passages, produces outputs that reflect specific 
operational context rather than generic parametric knowledge. 
Gao et al. (2023) provide a comprehensive taxonomy of RAG architectures that 
distinguishes between three levels of architectural sophistication. Basic RAG employs a 
single retrieval step followed by a single generation pass—a design that is simple and 
computationally efficient but may be insufficient for queries where relevant knowledge 
cannot be identified from the initial query alone. Advanced RAG introduces pre-retrieval 
query reformulation and post-retrieval re-ranking, improving retrieval quality at the cost 
of additional processing. Modular RAG supports iterative and adaptive retrieval 
strategies in which the system can retrieve additional information at multiple points 
during generation, guided by the content of previously retrieved passages. Gao et al. 
(2023) demonstrate that this architectural progression produces consistent improvements 
on tasks requiring multi-hop reasoning, which directly motivates the agentic multi-step 
design adopted in the present research. 
Asai et al. (2023) take this reasoning further with Self-RAG, a framework in which a 
language model learns to adaptively control its own retrieval behavior—deciding, at each 
point during generation, whether additional retrieval is warranted based on what has been 
generated so far. Their experiments demonstrate that adaptive retrieval improves both 
accuracy and efficiency of RAG systems on tasks with heterogeneous knowledge 
requirements. The agentic controller in the present research implements a conceptually 
similar adaptive logic through the ReAct reasoning loop: at each step, the controller 
assesses whether additional retrieval is warranted before proceeding. 

Es et al. (2023) introduce RAGAS, a framework for automated evaluation of RAG 
systems that assesses three dimensions of output quality: faithfulness, which measures the 
degree to which generated outputs are supported by retrieved documents; answer 
relevance, which measures the relevance of the generated response to the original query; 
and context relevance, which measures the relevance of retrieved documents to the query. 
RAGAS provides a principled basis for evaluating not just detection accuracy of the 
proposed RAG-based log analysis system, but the quality of the reasoning chain that 
connects retrieved knowledge to generated outputs—directly informing the evaluation 
methodology adopted for RQ3 of the present research. 
2.7 Agentic AI and Multi-Step Reasoning 
Agentic AI systems represent a qualitative extension of standard LLM capabilities that 
has attracted substantial research attention since 2022. Where a standard LLM generates 
a response to a prompt in a single forward pass, an agentic system executes an iterative 
loop in which the model reasons about what action to take, executes that action, observes 
the result, updates its reasoning state, and decides whether to continue or conclude. This 
architecture enables adaptive, multi-step problem solving under uncertainty that is not 
accessible to single-pass systems regardless of their scale or the sophistication of their 
prompting. 
Yao et al. (2023) introduced ReAct, Reasoning and Acting, as a framework for 
interleaving chain-of-thought reasoning with concrete action execution in language 
models. The central contribution of ReAct is the demonstration that reasoning and acting 
are mutually reinforcing: chain-of-thought reasoning improves the quality of action 
selection by making the model's analytical state explicit before each action, while 
observations from executed actions provide new information that refines subsequent 
reasoning steps. In a series of multi-hop question-answering and interactive decision-
making benchmarks, ReAct outperformed both standard prompting and chain-of-thought 
prompting without action capabilities, with improvements of up to 34% on tasks 
requiring multi-step information retrieval. The implications for log analysis are direct: a 
log sequence that cannot be classified from a single retrieval step because relevant 

context is distributed across multiple knowledge sources is exactly the kind of task that 
ReAct's interleaved reasoning-and-acting architecture is designed to handle. 
Schick et al. (2023) introduced Toolformer, demonstrating that language models can 
learn to use external tools—including search APIs, calculators, and structured 
databases—in a self-supervised manner, without requiring explicit tool-use supervision. 
By including tool calls within training data and training the model to predict when and 
how to invoke tools based on context, Toolformer models acquire the ability to retrieve 
and incorporate external information at the points where it is most needed. While the 
present research does not use Toolformer directly, its findings establish the feasibility of 
autonomous tool use in LLM-based systems and provide theoretical grounding for the 
design principle of the agentic controller—that knowledge retrieval should be driven by 
the model's own assessment of what information is needed at each reasoning step. 
Wang et al. (2023), in a comprehensive survey of LLM-based autonomous agents, 
identify memory, planning, and action as the three core capability dimensions that 
determine agent performance. Memory encompasses both short-term context—the 
current reasoning state—and long-term storage through external knowledge bases. 
Planning encompasses task decomposition and self-reflection—the capacity to critique 
and revise earlier reasoning steps in light of new evidence. Action encompasses the set of 
tools and external operations available to the agent. The agentic controller in the present 
research implements each of these dimensions: short-term memory through the reasoning 
chain data structure, long-term memory through the FAISS knowledge base, planning 
through the ReAct loop with up to five reasoning steps, and action through five defined 
action types. Wang et al. (2023) document that this combination of capabilities enables 
agentic systems to handle tasks of significantly greater complexity than single-pass 
systems, particularly in domains where relevant information is distributed and the correct 
analytical path is not apparent from the initial query alone. 
It is important to acknowledge that agentic AI introduces practical challenges that must 
be managed carefully. Longer inference chains increase computational cost, as each 
reasoning step requires an independent LLM call. Error propagation is a documented 
concern: incorrect reasoning in early steps can lead subsequent steps to build on faulty 

premises, compounding rather than correcting the initial mistake. Wang et al. (2023) also 
note that evaluating agentic systems is considerably more complex than evaluating 
single-pass models, because performance depends not only on the quality of the final 
output but on the quality of the intermediate reasoning trajectory. 
2.8 Evaluation Frameworks 
The evaluation of log analysis systems requires careful attention to both dataset selection 
and metric design, since choices in both dimensions can substantially influence 
conclusions drawn. He et al. (2020) introduced Loghub, a collection of nineteen system 
log datasets from diverse computing environments including distributed systems, 
supercomputers, and operating systems. Two datasets from Loghub have become the 
dominant benchmarks in the log analysis literature and are adopted for evaluation in the 
present research. The HDFS dataset contains approximately eleven million log entries 
from a Hadoop Distributed File System cluster, with ground-truth anomaly labels at the 
block level. The BGL dataset contains approximately 4.7 million entries from a 
BlueGene/L supercomputer, with message-level labels indicating hardware and software 
faults of various types. Together, these datasets provide sufficient scale and label 
coverage for statistically meaningful comparative evaluation, and their widespread use in 
the literature makes results directly comparable to prior published work. 
Le and Zhang (2022) provide an important methodological caveat regarding benchmark 
evaluation that is directly relevant to the design of the present research. In systematic 
evaluation of log parsing methods across multiple datasets, they demonstrate that 
reported performance figures are sensitive to sampling strategy, the proportion of 
anomalous examples in the test set, and the specific train/test split adopted. Methods that 
appear to perform similarly under idealized evaluation conditions can diverge 
substantially when evaluated under more demanding conditions—a finding that motivates 
the use of stratified sampling and repeated experimental trials in the present research, 
alongside paired t-tests for statistical significance testing. 
Standard detection metrics—precision, recall, F1-score, and false positive rate—provide 
the quantitative backbone of performance comparison across the four systems evaluated 
in this research. However, Chen et al. (2023) make a compelling case that these metrics 

are insufficient for evaluating systems intended to support human decision-making in 
operational monitoring contexts. A system that achieves a high F1-score but generates 
alerts that provide no actionable guidance is of limited practical value, regardless of its 
technical detection accuracy. Chen et al. (2023) propose supplementary evaluation 
protocols that assess the completeness and actionability of generated explanations, 
directly informing the qualitative evaluation rubric adopted for RQ3. 
Es et al. (2023), through the RAGAS framework, contribute an automated evaluation 
methodology for RAG-specific quality dimensions that extends beyond detection metrics. 
RAGAS assesses faithfulness—the degree to which generated outputs are supported by 
retrieved documents rather than derived from unconstrained parametric knowledge—
alongside answer relevance and retrieval precision. Faithfulness is particularly pertinent 
to the present research because it provides a proxy for the hallucination risk identified as 
a critical limitation of standalone LLM approaches. A high faithfulness score provides 
evidence that the proposed system's outputs are grounded in retrieved operational 
knowledge rather than fabricated.

Chapter 3 
METHODOLOGY 
3.1 Introduction 
This chapter describes the methodological decisions that govern how the research 
questions presented in Chapter 1 are investigated. It begins by articulating the 
philosophical position that underpins the inquiry before justifying the choice of 
comparative experimental design as the overarching research strategy. The chapter then 
specifies the variables under investigation, describes the software development lifecycle 
adopted for building the systems under comparison, and provides a detailed account of 
the dataset selection rationale, evaluation metrics, and statistical approach used to 
interpret results. 
3.2 Research Philosophy and Paradigm 
The research is grounded in a positivist philosophical tradition, which holds that 
knowledge is best produced through objective, empirically verifiable evidence obtained 
under controlled conditions (Creswell and Creswell, 2022). This position is appropriate 
for the present study because the research questions are fundamentally quantitative: they 
ask whether one computational approach produces measurably better outcomes than 
others, and they can be answered through numerical metrics derived from controlled 
experiments. The ontological stance is one of objective realism—the phenomena under 
investigation, namely anomaly detection accuracy and alert quality, are assumed to exist 
independently of the researcher and to be amenable to measurement. The epistemological 
stance is empiricist: claims are validated through observation rather than theory alone. 

A purely positivist approach does require qualification in the context of RQ3, which asks 
about the quality of alert outputs—a dimension that cannot be reduced to a single 
numerical metric without interpretive judgement. To accommodate this, the methodology 
incorporates a structured qualitative assessment of alert content alongside the quantitative 
detection experiments. This mixed-method approach—predominantly quantitative, with a 
qualitative component for alert quality evaluation—is consistent with Saunders et al. 
(2023), who argue that pragmatic mixed-method designs are appropriate when a single 
paradigm cannot fully address all dimensions of a research question. 
3.3 Research Design 
The primary research design adopted is a comparative experimental framework, in which 
multiple systems—the proposed agentic RAG framework and three baseline systems—
are evaluated on the same inputs under identical conditions, and their outputs are 
compared using pre-specified metrics. This design is well-suited to RQ1 and RQ2, both 
of which require direct, evidence-based comparison of system performance across 
approaches. Comparative experimental design enables the isolation of the independent 
variable—the choice of log analysis approach—while controlling for confounding factors 
such as dataset characteristics, evaluation procedure, and implementation quality. Where 
confounding cannot be fully eliminated, the use of statistical significance testing provides 
a mechanism for distinguishing genuine performance differences from noise in the 
experimental results (Field, 2024). 
This design has strong precedent in the log analysis literature. He et al. (2020) employ 
comparative experimental evaluation across multiple approaches and datasets as the 
standard methodology for assessing log analysis systems, and Le and Zhang (2022) 
extend this tradition by emphasizing the importance of evaluation under realistic 
conditions with stratified sampling and multiple experimental runs. The present research 
follows both precedents: all four systems are evaluated on the same HDFS and BGL test 
sets, produced by the same stratified 70/30 split, with statistical significance testing 
applied to validate observed differences. For RQ3, which requires qualitative assessment 
of alert content, the comparative framework is extended through the structured rubric 

evaluation, maintaining the comparative logic while accommodating the inherently 
interpretive nature of alert quality assessment.

However, Agile's suitability depends on specific contextual factors that do not apply 
uniformly to all software development endeavors, and careful analysis of the present 
project's characteristics leads to the conclusion that Waterfall is the more appropriate 
choice. 
Agile methodologies are designed to accommodate evolving requirements through 
iterative delivery and frequent stakeholder feedback. Their value is greatest in 
environments where requirements are ambiguous, users are actively involved in shaping

providing iterative feedback on functional requirements. The deliverable is not a

criteria. In this context, the iterative flexibility that makes Agile valuable in commercial 
product development provides no particular benefit.

3.6 Dataset Selection and Preparation 
Two publicly available, labeled log datasets are selected for evaluation: the Hadoop 
Distributed File System (HDFS) dataset and the BlueGene/L (BGL) supercomputer 
dataset. Both are drawn from the Loghub benchmark collection maintained by He et al. 
(2020), which provides standardized versions of both datasets alongside detailed 
descriptions of their provenance and label generation procedures. The selection of these 
two datasets is justified on four grounds. 
First, both datasets provide ground-truth anomaly labels, which are a prerequisite for 
quantitative evaluation of detection performance. The absence of ground-truth labels is 
one of the most common barriers to rigorous evaluation in the log analysis literature. 
Second, both datasets are sufficiently large to support statistically meaningful evaluation: 
the HDFS dataset contains approximately eleven million log entries with block-level 
anomaly labels, while BGL contains approximately 4.7 million entries with message-
level fault labels. Third, both datasets are widely used as benchmarks in the log analysis 
literature, which means that results obtained here can be directly compared to published 
figures. Fourth, the two datasets differ significantly in their structural characteristics, 

which provides the basis for the cross-dataset comparison motivating RQ2: HDFS logs 
are generated by a distributed storage system and exhibit block-level failure patterns 
driven by data replication faults, whereas BGL logs originate from a supercomputer and 
exhibit hardware and system fault patterns with distinct temporal signatures. This 
structural heterogeneity means that findings consistent across both datasets carry greater 
external validity than findings derived from a single dataset alone. 
Dataset preparation follows a standardized procedure for all four systems to ensure 
comparability. Raw log files are parsed using the Drain3 algorithm with a fixed-depth 
tree of depth four and a similarity threshold of 0.4. A 70/30 stratified train/test split is 
applied, where stratification is performed on the anomaly label to ensure that the 
proportion of anomalous examples in the test set reflects their proportion in the full 
dataset. This is particularly important for the HDFS and BGL datasets, in which 
anomalous logs represent a minority class.

3.8 Technology Stack Justification 
All systems are implemented in Python 3.12, which provides the most extensive 
ecosystem of machine learning, natural language processing, and data analysis libraries 
and is the de facto standard for research prototyping in these domains. The specific 
library choices are justified with reference to the functional requirements of the system 
and the constraints of a single-developer academic project. 
Log parsing is performed using Drain3—the Python implementation of the Drain log 
parsing algorithm. Drain3 is selected because it operates online, processing logs 

incrementally rather than requiring full dataset ingestion before parsing begins. The 
vector knowledge base is implemented with FAISS (Facebook AI Similarity Search), 
specifically the IndexFlatL2 index type, using sentence embeddings generated by the all-
MiniLM-L6-v2 model from the sentence-transformers library. FAISS is chosen for its 
computational efficiency—exact nearest-neighbor search completes within the 500ms 
latency budget—and for its broad adoption in RAG system implementations. 
The LLM component uses Mistral 7B Instruct, served locally via Ollama. The choice of a 
locally-served open-source model rather than a commercial API such as OpenAI GPT-4 
is motivated by three considerations. First, local inference ensures complete 
reproducibility: the model version and inference parameters are fixed and under the 
researcher's direct control. Second, using a 7B parameter model constrains the 
performance of the LLM component in a way that is consistent with the research 
question: the goal is to demonstrate that the agentic reasoning architecture adds value, not 
merely that a larger model produces better outputs. Third, local inference eliminates per-
token API costs. 
3.9 Ethical Considerations 
The research raises three categories of ethical consideration. First, data privacy: both 
datasets used—HDFS and BGL—are publicly available and fully anonymized, 
containing no personal identifiable information. They are distributed for research 
purposes under terms that permit academic use, and no data collection from human 
participants is involved. Second, responsible design of automated alerting systems: the 
proposed system addresses this through confidence scores attached to every alert and 
reasoning chains that enable operators to verify the basis of classification before acting. 
Third, the risk of over-automation: the system is designed as a decision-support tool 
rather than an autonomous decision-making system. 
3.10 Limitations of the Methodology 
Several limitations are acknowledged. First, the evaluation is conducted on two 
benchmark datasets under controlled experimental conditions rather than in a live 
production environment. Second, the LLM component uses Mistral 7B—a model 
considerably smaller than frontier models available at the time of writing. Third, the 

qualitative alert quality evaluation for RQ3 is conducted by a single evaluator, which 
introduces the risk of rater bias. Fourth, the Isolation Forest baseline uses a fixed set of 
seven engineered features.

SYSTEM DESIGN AND ARCHITECTURE 
4.1 Introduction 
This chapter presents the architecture of the proposed agentic RAG framework and 
describes the design of the three baseline systems against which it is compared. The 
chapter begins with a high-level system overview before examining each major 
component in detail: the log preprocessing module, the vector knowledge base, the 
agentic controller, and the alert generator. The chapter concludes by describing the 
architecture of the three baseline systems: the rule-based matcher, the Isolation Forest 
classifier, and the non-agentic RAG system. 
4.2 System Overview 
The proposed agentic RAG framework comprises four major components that operate 
sequentially to transform raw log entries into structured, actionable alerts. Figure 4.1 
presents the system architecture and the data flow between components. 

 
Figure 4.1: System architecture overview showing data flow from raw logs through 
preprocessing, knowledge retrieval, agentic reasoning, to alert generation 
The first component, the log preprocessing module, accepts raw log entries as 
unstructured text and produces structured representations containing the log template, 
extracted variable fields, severity level, and source component. This structured 
representation is the input to all downstream analysis. The second component, the vector 
knowledge base, stores domain knowledge documents, historical incident reports, and 
error pattern descriptions as dense vector embeddings. When queried with a log entry, it 
returns the k most semantically similar documents. The third component, the agentic 
controller, implements the ReAct reasoning loop. It receives the preprocessed log and 
executes up to five reasoning steps, where each step involves deciding whether to retrieve 
additional knowledge, revise the current assessment, or produce a final classification and 
explanation. The fourth component, the alert generator, receives the controller's output—
including the classification decision, confidence score, and accumulated reasoning 

chain—and produces a structured alert with component identification, root cause 
explanation, and recommended actions. 
The system is designed around three architectural principles. First, modularity: each 
component has a clearly defined interface and can be developed, tested, and validated 
independently. Second, transparency: every decision made by the system—from log 
parsing to final alert generation—is recorded in a reasoning chain that can be inspected 
and audited. Third, adaptability: the agentic controller adjusts its analytical approach 
based on the content of the log and the results of intermediate reasoning steps, rather than 
following a fixed processing sequence. These principles are not merely abstract design 
goals; they directly address the limitations of existing approaches identified in Chapter 2. 
Modularity ensures that individual components can be replaced or upgraded without 
redesigning the entire system. Transparency addresses the interpretability gap of machine 
learning methods. Adaptability addresses the rigidity of rule-based systems by enabling 
the system to handle novel failure patterns through iterative reasoning rather than 
requiring pre-specification of all possible scenarios. 
4.3 Log Preprocessing Module 
Raw system logs are semi-structured text with variable formatting, inconsistent 
timestamp representations, and embedded dynamic values that vary across log instances 
even when the underlying event is identical. The log preprocessing module normalizes 
this heterogeneous input into a consistent structured representation. Figure 4.2 illustrates 
the transformation pipeline. 
 
Figure 4.2: Log preprocessing pipeline showing transformation from raw log entry to structured 
representation with template extraction, variable masking, and metadata enrichment 

The module implements the Drain3 algorithm, which builds a fixed-depth parse tree by 
grouping log entries that share similar token structures. Each group corresponds to a log 
template—the invariant portion of a log message with variable fields replaced by 
wildcards. For example, the log entry 'User alice logged in from IP 192.168.1.10 at 2024-
03-15 09:32:17' would be parsed to the template 'User <*> logged in from IP <*> at <*>' 
with three extracted variables: alice, 192.168.1.10, and 2024-03-15 09:32:17. The 
template becomes the primary identifier for the log event type, while the variables are 
retained for contextual analysis. 
The module enriches each parsed log with metadata extracted from the raw entry or 
inferred from the template. Severity level—categorized as CRITICAL, ERROR, 
WARNING, INFO, or DEBUG—is extracted from explicit severity markers in the raw 
log or inferred from the presence of keywords like 'fatal', 'exception', or 'timeout'. Source 
component is extracted from structured fields if present, or inferred from component 
names appearing in the log template. Timestamp is normalized to ISO 8601 format. The 
output of the preprocessing module is a structured JSON object containing the template 
ID, the original raw log, extracted variables, severity level, source component, and 
normalized timestamp. This structured representation is the input to both the knowledge 
base query encoder and the agentic controller.

4.5 Agentic Controller 
The agentic controller is the central reasoning component of the proposed framework. It

interleaves chain-of-thought reasoning with concrete actions. The controller receives a 

preprocessed log entry as input and produces a classification decision, confidence score, 
and natural language explanation as output. Figure 4.3 presents the control flow.

The action selection mechanism uses structured prompting to constrain the LLM's output. 
The controller provides the LLM with a description of the available actions and instructs 
it to output the selected action in a specific JSON format. If the selected action is 
RETRIEVE, the controller extracts the query string from the LLM's output, queries the

selected action is REVISE_SEVERITY, IDENTIFY_COMPONENT, or 
EXPLAIN_CAUSE, the controller extracts the updated assessment from the LLM's 
output and records it in the reasoning state. If the selected action is FINALIZE, the loop 
terminates and the accumulated reasoning state is passed to the alert generator. 
The loop continues until one of three termination conditions is met. First, the controller 
selects the FINALIZE action, indicating that it has accumulated sufficient evidence to 
make a confident classification decision. Second, the maximum iteration count of five is 
reached, at which point the loop terminates regardless of whether the controller has 
selected FINALIZE. Third, if two consecutive iterations produce identical reasoning 
steps—indicating that the controller has reached a fixed point and is no longer making 
progress—the loop terminates early to prevent unproductive iteration. 
The accumulated reasoning chain—the sequence of reasoning steps, selected actions, and 
retrieved knowledge from all iterations—is preserved and passed to the alert generator. 
This chain provides the complete audit trail of the controller's analytical process and 
forms the basis of the natural language explanation included in the final alert. The 
preservation of the reasoning chain addresses the interpretability limitation identified in 
Chapter 2: unlike machine learning classifiers that produce only a numerical score, the 
agentic controller produces a natural language trace that makes its analytical process 
auditable and allows operators to verify the basis of its decisions. 

4.6 Alert Generator 
The alert generator receives the agentic controller's output—the classification decision, 
confidence score, and reasoning chain—and produces a structured alert formatted for 
consumption by system operators. Figure 4.4 presents the alert template structure. 
[Figure 4.4: Alert output template showing structured fields: timestamp, severity, affected 
component, anomaly classification, confidence score, reasoning summary, root cause 
explanation, and recommended actions] 
Figure 4.4: Alert output template showing structured fields: timestamp, severity, affected component, 
anomaly classification, confidence score, reasoning summary, root cause explanation, and recommended 
actions 
The alert comprises eight fields. The timestamp field records when the alert was 
generated. The severity field reflects the final severity assessment from the agentic 
controller, which may differ from the original log severity if the controller revised it 
during reasoning. The affected component field identifies the system component or 
service implicated in the anomaly. The classification field contains the binary anomaly 
decision: ANOMALOUS or NORMAL. The confidence score is a numerical value 
between 0 and 1 reflecting the controller's certainty in its classification. The reasoning 
summary provides a condensed natural language description of the analytical process, 
extracted from the reasoning chain by identifying the key observations and inferences 
made across iterations. The root cause explanation presents the controller's assessment of 
what caused the anomaly, drawn from the EXPLAIN_CAUSE action output or inferred 
from the retrieved knowledge. The recommended actions field contains specific 
operational steps the operator should take in response to the alert, drawn either from 
retrieved remediation documents in the knowledge base or generated by the LLM based 
on the identified root cause. 
This structured format directly addresses the actionability requirement identified in RQ3. 
Each alert provides not only a detection decision but also the context necessary for an 
operator to understand what happened, why it matters, and what to do about it. The 
confidence score enables operators to triage alerts by certainty: high-confidence alerts 
can be acted upon immediately, while low-confidence alerts may warrant additional 

investigation before action. The reasoning summary and root cause explanation provide 
the interpretability that machine learning methods lack, while the recommended actions 
provide concrete guidance that rule-based systems do not offer. 
4.7 Baseline System Designs 
Three baseline systems are implemented for comparative evaluation. Each represents a 
distinct category of log analysis approach and is designed to operate on the same 
preprocessed log inputs as the proposed agentic RAG framework. Figure 4.5 presents the 
architecture of all three baselines. 
 
Figure 4.5: Baseline system architectures: (a) Rule-based keyword matcher, (b) Isolation Forest classifier 
with feature extraction, (c) Non-agentic single-pass RAG system 
Baseline 1: Rule-Based Keyword Matcher. This system implements a representative 
rule-based approach. It maintains a dictionary of 25 anomaly-indicating keywords 
extracted from the training data, including terms like 'error', 'exception', 'timeout', 'failed', 
and 'critical'. A log is classified as anomalous if its template or variable fields contain any 
keyword from the dictionary, and as normal otherwise. Alerts generated by this system 
include the matched keyword and the log template, but no root cause analysis or 
recommended actions. This baseline represents the most widely deployed approach in 
production environments and provides the lower bound of expected performance. 
Baseline 2: Isolation Forest Classifier. This system implements an unsupervised 
machine learning approach. Each preprocessed log is converted into a seven-dimensional 

feature vector: template frequency (number of times this template appeared in the training 
set), severity level (encoded as an integer 0-4), log length in characters, number of 
extracted variables, hour of day, inter-arrival time since the previous log from the same 
component, and template entropy (computed from the distribution of variable values for 
this template in the training set). An Isolation Forest model with 100 trees and 
contamination parameter set to the true anomaly rate in the training set is trained on these 
features. At inference time, logs with anomaly scores above the contamination threshold 
are classified as anomalous. This baseline provides no explanation for its decisions—only 
a numerical anomaly score. It represents the classical machine learning approach to log 
anomaly detection. 
Baseline 3: Non-Agentic Single-Pass RAG. This system implements the standard RAG 
architecture without agentic reasoning. It uses the same knowledge base and retrieval 
mechanism as the proposed framework, but instead of iterating through multiple 
reasoning steps, it performs a single retrieval and generation pass. The preprocessed log 
is used to query the knowledge base once, the three most similar documents are retrieved, 
and the LLM generates a classification decision and explanation in a single inference call. 
This baseline isolates the contribution of the agentic reasoning loop: by comparing it to 
the proposed framework, we can determine whether the multi-step iterative approach 
provides meaningful advantage over the simpler single-pass RAG design.

5.4 Log Preprocessing Implementation 
The preprocessing module wraps the Drain3 library to handle log parsing and 
normalization. Figure 5.2 shows the processing pipeline implemented in the 
LogPreprocessor class. 
 
Figure 5.2: Log preprocessing implementation showing data flow: raw log input, Drain3 parsing, template 
extraction, variable masking, metadata enrichment, structured output 
The LogPreprocessor class maintains an internal Drain3 TemplateMiner instance 
configured with depth=4, sim_th=0.4, and max_children=100. These parameters were 
selected based on preliminary experiments on a validation subset of the HDFS dataset. 

The depth parameter controls the height of the internal parse tree—deeper trees provide 
finer-grained template extraction at the cost of higher memory usage. The similarity 
threshold sim_th determines when two log entries are considered similar enough to share 
a template—lower values produce more templates with greater specificity, while higher 
values merge more logs into fewer templates. The max_children parameter limits the 
branching factor at each tree node to prevent memory exhaustion on highly variable logs. 
When a raw log is processed, the LogPreprocessor calls the Drain3 match() method, 
which returns a template ID and the list of extracted variables. Severity extraction uses 
regular expressions to identify keywords like 'CRITICAL', 'ERROR', 'WARN', 'INFO', or 
'DEBUG' in the raw log text. If no explicit severity marker is found, the module applies 
heuristic rules: logs containing 'fatal', 'exception', or 'abort' are assigned CRITICAL; logs 
containing 'error', 'fail', or 'timeout' are assigned ERROR; all others default to INFO. 
Component extraction searches for component names in a predefined list—for HDFS, 
this includes 'NameNode', 'DataNode', and 'HDFS Client'—and assigns the first match 
found. Timestamps are parsed using the dateutil library and normalized to ISO 8601 
format. 
The output is a structured dictionary containing template_id, template_text, variables, 
severity, component, timestamp, and raw_log. This dictionary is serialized to JSON and 
passed to downstream components. The entire preprocessing implementation consists of 
180 lines of code including configuration, error handling, and logging statements.

5.6 Agentic Controller Implementation 
The agentic controller implements the ReAct reasoning loop using LangChain's agent 
framework. Figure 5.3 illustrates the implementation architecture. 

 
Figure 5.3: Agentic controller implementation architecture showing LangChain integration, action 
execution flow, reasoning state management, and termination logic 
The core class is AgenticController, which maintains the reasoning state across iterations 
and orchestrates interaction between the LLM and the knowledge base. The reasoning 
state is a Python dictionary containing the current log entry, all retrieved documents from 
previous iterations, the accumulated reasoning chain, the current severity assessment, 
identified component, and proposed root cause. This state is updated after each iteration 
and passed to the LLM as context for the next reasoning step. 
The ReAct loop is implemented as a while loop with a maximum iteration count of 5. At 
each iteration, the controller constructs a prompt containing the system instruction, the 
current reasoning state, and a request for the next reasoning step and action. The system 
instruction defines the five available actions, specifies the expected output format (JSON 
with 'reasoning' and 'action' fields), and provides examples of correct action selection. 

The prompt is sent to the Mistral 7B model through Ollama's API. The response is parsed 
as JSON, and the selected action is extracted. Table 5.3 shows the action execution logic.

After executing the selected action, the reasoning step and action are appended to the 
reasoning chain. The loop continues until one of three termination conditions is met: the 
FINALIZE action is selected, the maximum iteration count is reached, or two consecutive 
iterations produce identical reasoning steps (indicating a fixed point). When the loop 
terminates, the controller computes a confidence score based on the number of iterations 
completed and whether FINALIZE was explicitly selected—loops that terminate via 
FINALIZE receive higher confidence scores than those that exhaust the iteration budget. 
The final output is a structured dictionary containing classification (ANOMALOUS or 
NORMAL), confidence score, reasoning chain, severity, component, and root cause. 
Error handling is implemented at multiple points: if JSON parsing fails, the controller 
retries the LLM call once with a clarified prompt; if the retry fails, the loop terminates 
and returns a low-confidence classification. The controller implementation is 420 lines of 
code. 
5.7 Alert Generator Implementation 
The alert generator receives the agentic controller's output and produces a formatted alert. 
The implementation is straightforward—a single AlertGenerator class with a generate() 
method that accepts the controller output dictionary and returns a formatted string. The 
method extracts the eight required fields from the input: timestamp is set to the current 

system time, severity and component are copied from the controller output, classification 
is the anomaly decision, confidence is the computed score, reasoning summary is 
generated by concatenating the reasoning chain with newline separators, root cause is 
copied from the controller output, and recommended actions are extracted from retrieved 
documents tagged with the 'remediation' category if present, or generated by a separate 
LLM call if no matching remediation document was retrieved. 
The formatted alert is a multi-line string with labeled fields, similar to an email header 
format. For example: 'ALERT | Timestamp: 2024-04-15 14:32:17 | Severity: CRITICAL | 
Component: DataNode | Classification: ANOMALOUS | Confidence: 0.87 | Reasoning: 
[chain] | Root Cause: [explanation] | Actions: [recommendations]'. This format is human-
readable and can be easily parsed by downstream monitoring systems. The generator 
implementation is 85 lines of code.

one. The consistent 4+ percentage point improvement across both datasets provides 
evidence that multi-step reasoning adds measurable value beyond what single-pass RAG 
achieves. This finding aligns with the theoretical predictions of Yao et al. (2023), who 
demonstrated that ReAct's interleaved reasoning-and-acting architecture improves 
performance on multi-hop reasoning tasks by enabling the model to refine its 
understanding through iterative retrieval and reflection. 
The comparison with Isolation Forest demonstrates that retrieval-augmented generation 
outperforms statistical machine learning methods that rely solely on numerical features. 
Isolation Forest achieves F1-scores around 0.80 on both datasets—respectable 
performance that substantially exceeds the rule-based baseline—but trails both RAG 
variants by 6-10 percentage points. This gap reflects the interpretability-performance 
tradeoff identified in Chapter 2: machine learning methods can achieve moderate 
detection accuracy, but they cannot generate the natural language explanations that RAG 
systems produce. The results demonstrate that this tradeoff is not fundamental—RAG 
systems achieve both higher accuracy and full interpretability. 
7.3 RQ2: Most Competitive Baseline 
RQ2 asked which baseline approach shows the greatest competitiveness compared to the 
proposed framework. The results unambiguously identify non-agentic RAG as the most 
competitive baseline. On HDFS, non-agentic RAG achieves F1=0.864 compared to the 
agentic system's 0.907—a gap of 4.3 percentage points. Isolation Forest trails by 10.1 
points and the rule-based system by 19.4 points. The pattern is identical on BGL. Non-

agentic RAG is not merely closer to the proposed system than other baselines; it is the 
only baseline that approaches competitive performance. 
This finding has theoretical and practical implications. Theoretically, it suggests that the 
combination of retrieval and generation is more important than the number of reasoning 
steps. The gap between rule-based and non-agentic RAG (15+ percentage points) is 
larger than the gap between non-agentic and agentic RAG (4 points). This indicates that 
retrieval-augmented generation addresses the most consequential limitations of traditional 
approaches—rigidity and lack of contextual knowledge—and that agentic reasoning 
provides incremental improvement rather than a qualitative leap. Practically, this suggests 
that organizations currently using rule-based or machine learning systems could achieve 
substantial performance gains by adopting even single-pass RAG, and that the additional 
complexity of agentic reasoning is justified only when the highest possible accuracy is 
required. 
The performance variation across baselines also illuminates what aspects of log analysis 
are most difficult. Isolation Forest achieves recall values (0.82 on HDFS, 0.79 on BGL) 
that are competitive with the agentic system's recall (0.89 and 0.86), but its precision is 
substantially lower (0.79 and 0.76 vs. 0.92 and 0.89). This indicates that statistical 
feature-based methods can identify most anomalies but generate excessive false positives 
because they lack the semantic understanding that distinguishes genuine faults from 
statistical outliers. RAG systems, by retrieving domain knowledge that contextualizes log 
patterns, achieve the precision that pure statistical methods cannot.

7.5 Comparison with Published Literature 
Comparing the results obtained here with published figures from the log analysis 
literature requires careful interpretation, as evaluation methodologies, datasets, and 
baseline implementations vary across studies. Guo et al. (2021) report F1-scores of 0.982 
on HDFS for LogBERT, substantially higher than the 0.907 achieved by the proposed 
system. However, their evaluation uses a different train/test split and excludes certain log 
types, making direct comparison problematic. Le and Zhang (2022) demonstrate that 
LogBERT's performance degrades substantially when evaluated on logs with format drift 
and label noise—conditions representative of live production environments—achieving 
F1-scores in the 0.85-0.90 range on realistic test sets. The proposed system's performance 
of 0.907 on HDFS and 0.871 on BGL falls within this range, suggesting that its 

performance is competitive with state-of-the-art deep learning methods under realistic 
conditions. 
More importantly, the proposed system addresses a limitation that LogBERT and other 
deep learning methods do not: interpretability. LogBERT produces numerical anomaly 
scores with no accompanying explanation. The proposed system produces reasoning 
chains and structured alerts that enable operators to understand and act on detected 
anomalies. This represents a qualitative advance that cannot be captured in F1-score 
comparisons alone. Chen et al. (2023) argue that the log analysis field has prioritized 
detection accuracy at the expense of decision support quality, and that future research 
must treat interpretability as a primary requirement rather than an optional supplement to 
detection performance. The present research demonstrates that high detection accuracy 
and full interpretability are not mutually exclusive. 
The agentic architecture draws on recent work by Yao et al. (2023) on ReAct and Wang 
et al. (2023) on LLM-based autonomous agents, but applies these frameworks to a 
domain—log analysis—where they have not previously been evaluated. Yao et al. (2023) 
report performance improvements of up to 34% on multi-hop question-answering tasks 
when using ReAct compared to standard prompting. The 4+ percentage point 
improvement observed here is more modest, which may reflect that log analysis is a more 
constrained task than open-domain question answering. Each log entry provides a 
specific analytical target, and the knowledge base is domain-focused rather than 
encyclopedic. Nevertheless, the consistent improvement across both datasets provides 
evidence that the ReAct pattern generalizes beyond the tasks for which it was originally 
developed. 
7.6 Practical Implications 
The results have implications for organizations operating distributed systems at scale. 
First, the substantial false positive rate reduction—from 32.4% for rule-based systems to 
7.8% for agentic RAG on HDFS—directly addresses the alert fatigue problem that 
degrades operator responsiveness in production monitoring environments. A false 
positive rate below 10% means that more than nine out of ten alerts are genuine, which 
maintains operator confidence in the monitoring system. Second, the alert quality results 

demonstrate that the system produces outputs suitable for immediate operational use. 
Alerts with average scores of 12.9/15 provide specific component identification, detailed 
root cause explanations, and concrete recommended actions—the information operators 
need to respond effectively without conducting additional investigation. 
Third, the comparison between agentic and non-agentic RAG provides guidance on when 
the additional complexity of multi-step reasoning is justified. For organizations 
prioritizing simplicity and minimal inference latency, single-pass RAG may provide the 
best cost-benefit tradeoff, achieving F1-scores around 0.85 with simpler implementation. 
For organizations where detection accuracy is paramount—financial trading systems, 
healthcare platforms, or critical infrastructure—the 4 percentage point improvement from 
agentic reasoning may justify the additional computational cost and implementation 
complexity. The cross-dataset consistency of results provides confidence that these 
performance characteristics generalize beyond the specific systems evaluated here. 
Fourth, the use of open-source components—Mistral 7B served locally through Ollama, 
FAISS for vector search, and Drain3 for log parsing—demonstrates that effective agentic 
RAG systems can be built without dependence on proprietary commercial APIs. This 
reduces operational cost, eliminates external service dependencies, and ensures that 
sensitive operational logs never leave the organization's infrastructure. The complete 
system implementation, excluding the LLM weights themselves, consists of under 1,200 
lines of Python code, suggesting that adoption barriers are primarily conceptual rather 
than technical. 
7.7 Limitations of This Research 
Several limitations must be acknowledged. First, the evaluation is conducted on two 
benchmark datasets under controlled experimental conditions rather than in live 
production environments. While both datasets are derived from real systems, they 
represent snapshots of historical data rather than streaming logs with the temporal 
dynamics and operational pressures of production monitoring. Second, the LLM 
component uses Mistral 7B—a model considerably smaller than frontier models available 
at the time of writing. Larger models might achieve higher performance, but evaluating 
this claim would require access to substantially greater computational resources. 

Third, the qualitative alert quality evaluation for RQ3 was conducted by a single 
evaluator, introducing the risk of rater bias. Inter-rater reliability assessment with 
multiple independent evaluators would strengthen confidence in the rubric scores. Fourth, 
the knowledge base contains 150 documents for HDFS and 120 for BGL, constructed 
specifically for this research. Real-world deployment would require substantially larger 
knowledge bases continuously updated as new failure patterns emerge and system 
components evolve. Fifth, the study does not evaluate inference latency or computational 
cost, both of which are relevant for production deployment. The multi-step agentic 
reasoning loop requires multiple LLM calls per log entry, which increases latency 
compared to single-pass methods.

8.4 Theoretical Implications 
The findings contribute to theoretical understanding of how retrieval-augmented 
generation and agentic reasoning improve performance on knowledge-intensive tasks. 
The consistent 4+ percentage point improvement of agentic over non-agentic RAG across 
structurally different datasets provides empirical support for the claim made by Yao et al.

theoretical mechanism is that multi-step reasoning enables the system to refine its 
understanding iteratively—retrieving knowledge, assessing whether additional context is 
needed, and adjusting its analysis based on what it learns. This aligns with human 
analytical processes more closely than single-pass inference. 
The finding that non-agentic RAG substantially outperforms machine learning baselines 
(6-10 percentage points) suggests that semantic understanding—the ability to reason 
about the meaning of log content rather than merely its statistical properties—is more 
valuable for anomaly detection than sophisticated statistical modeling. This has 
implications beyond log analysis for any domain where context and domain knowledge 
are required to interpret observations correctly. Tasks characterized by high semantic 
complexity and availability of relevant external knowledge are prime candidates for 
RAG-based approaches. 
8.5 Practical Implications 
For practitioners operating distributed systems, the findings suggest that agentic RAG 
systems can deliver detection performance competitive with state-of-the-art deep learning 
methods while providing the interpretability that machine learning approaches lack. The 
7.8% false positive rate achieved on HDFS is low enough to maintain operator trust in the 
monitoring system, while the detailed reasoning chains enable operators to verify alert 
validity before taking action. The use of open-source components—Mistral 7B, FAISS, 

Drain3—demonstrates that effective systems can be built without commercial API 
dependencies, reducing operational cost and ensuring sensitive logs never leave 
organizational infrastructure. 
The comparison between agentic and non-agentic RAG provides decision guidance.

complete implementation in under 1,200 lines of Python code suggests adoption barriers 
are primarily conceptual rather than technical.

This dissertation has demonstrated that agentic retrieval-augmented generation can 
improve both detection accuracy and alert actionability in system log analysis. The 
proposed framework achieves F1-scores of 0.907 on HDFS and 0.871 on BGL, 
outperforming rule-based, machine learning, and single-pass RAG baselines with 
statistical significance. Alert quality scores of 12.9/15 demonstrate that the system 
produces outputs suitable for operational use. The findings contribute to theoretical 
understanding of how multi-step reasoning improves performance on knowledge-

intensive tasks and provide practical guidance for organizations seeking to improve their 
log monitoring capabilities. The open-source implementation demonstrates that effective 
agentic systems can be built with accessible tools. While several limitations remain—
particularly the need for live production validation—the results provide strong evidence

B.1 Error Pattern Document: HDFS Block Replication Failure 
Document Category: Error Patterns 
Document ID: EP_HDFS_001 
Content: 
HDFS Block Replication Failure Pattern 
 
Description: This failure pattern occurs when a DataNode is unable to complete block 
replication to another DataNode. The typical signature includes: 
- IOException with message 'Block does not exist' 
- PacketResponder termination before completion 
- SocketException with 'Connection reset' 
 
Common Causes: 
1. Target DataNode crashed or became unavailable during transfer 
2. Network connectivity issues between DataNodes 
3. Disk failure on target DataNode 
4. DataNode process killed during block transfer 
 
Impact: Under-replication of data blocks. If replication factor drops below configured 
minimum, data loss risk increases. Critical for blocks with replication factor of 1. 
 
Related Components: DataNode, PacketResponder, DataXceiver, Block Transfer 
Protocol 

 
B.2 Component Documentation: BGL RAS Kernel 
Document Category: Component Documentation 
Document ID: CD_BGL_002 
Content: 
BlueGene/L RAS Kernel Component 
 
Description: The Reliability, Availability, and Serviceability (RAS) kernel is the central 
component responsible for monitoring system health and reporting hardware and 
software events on BlueGene/L supercomputers. 
 
Key Responsibilities: 
- Collecting events from compute nodes, I/O nodes, and system components 
- Classifying events by severity (INFO, WARNING, SEVERE, FATAL) 
- Managing communication between compute nodes and I/O nodes via ciod 
- Logging hardware failures, network errors, and system anomalies 
 
ciod (Compute I/O Daemon): Mediates I/O operations between compute nodes and I/O 
nodes. Failures in ciod indicate communication breakdowns that prevent compute nodes 
from performing file I/O operations. 
 
Event Severity Levels: 
- INFO: Normal operations, informational messages 
- WARNING: Potential issues that do not impact functionality 
- SEVERE: Errors requiring attention, may impact performance 
- FATAL: Unrecoverable errors requiring intervention 
 

B.3 Remediation Action: DataNode Block Replication Recovery 
Document Category: Remediation Actions 
Document ID: RA_HDFS_003 
Content: 
Remediation Procedure: HDFS Block Under-Replication Recovery 
 
Symptoms: Blocks showing replication factor below configured minimum, DataNode 
communication failures during block transfer. 
 
Immediate Actions: 
1. Identify affected blocks using: hdfs fsck / -files -blocks -locations 
2. Check DataNode health: hdfs dfsadmin -report 
3. Verify network connectivity between DataNodes 
4. Review DataNode logs for error patterns 
 
Recovery Steps: 
1. If DataNode is healthy but network failed: Wait for network recovery, HDFS will 
automatically re-replicate 
2. If DataNode crashed: Restart DataNode service, monitor block replication progress 
3. If DataNode disk failed: Decommission failed DataNode, add replacement, trigger 
rebalancing 
4. Manual replication trigger (if needed): hdfs dfsadmin -triggerBlockReport <datanode> 
 
Verification: 
- Run fsck again after 10 minutes to verify replication recovery 
- Monitor NameNode logs for under-replicated block count 
- Check that replication factor returns to configured level
